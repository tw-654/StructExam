## 1 引言

### 1.1 编写目的

本报告对 **StructExam 全平台**（学生端、教师端、管理员端）在 **Docker 部署形态** 下的测试执行情况进行汇总，对照测试计划陈述**实际结果与发现**，给出功能与质量方面的**结论与评价**，并对缺陷、限制与后续工作提出建议。

**预期读者**：项目经理、测试负责人、前后端开发、运维、教学管理方（用户代表）。

### 1.2 背景

**a.** 被测软件系统名称：**StructExam 数据结构机考平台**（学生端、教师端、管理员端 Web + 经网关的 REST API）。

**b.** 任务提出者、开发者、用户及计算中心：以项目仓库及组织内立项/合同为准（本仓库未附任务书扫描件）。

**本次测试环境**：在 **Windows 10 + Docker Desktop 4.x** 上执行 **`docker compose up -d`**（项目根目录），包含以下服务：
- **基础设施**：`mysql:8.0`（端口映射 `3307:3306`）、`redis:7.0`、`nacos:2.2.3`
- **微服务**：`gateway`（端口 `8080`）、`user-service`、`exam-service`、`code-service`
- **前端**：`frontend`（Nginx 静态 + `/api` 代理，端口映射 `80:80`）
- **分布式判题**：`sandbox-node-1/2/3`（端口 `18091-18093`）
- **测试工具**：`playwright-tests`（容器化执行）、`jmeter`（容器化执行，`structexam-jmeter:latest`）

**Playwright** 使用 **`E2E_BASE_URL=http://frontend`**（Docker 网络内访问前端容器）及测试账号环境变量；**JMeter** 在 **容器内** 通过 `gateway:8080` 访问（Docker Compose 网络，直连网关）。

**测试环境与生产/机房环境的差异及影响**：

| 差异项 | 本次测试环境 | 对结果的影响 |
|--------|----------------|----------------|
| 单机 Docker | 全栈同机运行、无多副本与负载均衡 | 未验证 K8s 下调度与网络策略；性能指标受单机资源限制 |
| MySQL 宿主端口 | 因本机 **3306 已被占用**，映射为 **`3307:3306`** | 仅影响宿主机直连 MySQL 调试；容器内仍用 `mysql:3306` |
| 浏览器 | Playwright Chromium（容器内） | 兼容性结论不覆盖 Safari/Firefox 全矩阵 |
| JMeter 运行方式 | 容器化 JMeter（`structexam-jmeter:latest`，基于 `eclipse-temurin:17-jdk-alpine + JMeter 5.6.3`） | 避免 Docker Hub 拉取失败问题，测试结果更稳定 |
| 种子数据 | 使用 `sql/init.sql`（包含测试用户：admin01、teacher01、student01、jmeter_docker_01） | 与生产数据形态不同；生产环境需单独评估 |
| 沙箱节点 | 3 个 sandbox-node 节点本地运行 | 分布式判题能力已验证；生产环境需更多节点 |
| 网络环境 | 本地 Docker 网络，无外部网络延迟 | 未验证跨网络环境下的性能表现 |

### 2.2 实施过程中对环境的修改（相对仓库原状）

为打通 **Docker 内网关 → 各微服务** 及 **Docker 前端 → 网关 API**，本次对代码/配置做了如下变更（均已落库）：

| 项 | 说明 |
|----|------|
| `backend/gateway/.../application-docker.yml` | 新增：`docker` Profile 下路由 `uri` 使用 `user-service` / `exam-service` / `code-service` 主机名，Redis 使用 `REDIS_HOST`（默认 `redis`） |
| `docker-compose.yml` | `gateway` 增加 `SPRING_PROFILES_ACTIVE: docker`；`depends_on` 增加各业务服务；**MySQL 端口映射改为 `3307:3306`**；sandbox-node 镜像改为 Ubuntu 基础镜像以加速构建 |
| `frontend/nginx.conf` | **`proxy_pass` 去掉末尾 `/`**，保留完整 `/api/**` 路径转发至网关（修复 Docker 下登录接口 404/失败） |
| `Dockerfile.sandbox-node` | 将基础镜像从 Alpine 改为 Ubuntu（`eclipse-temurin:17-jdk-jammy`），解决 gcc/g++ 安装耗时过长问题 |

**数据说明与脚注（2026-05-27 优化后测试）：**
- `login-performance-baseline.jmx`（推荐参考）：登录性能基线测试，分离低/中并发场景，添加性能基线断言（P95<3秒），数据可靠。优化后登录P95=3,969.6ms，符合BCrypt cost=10预期
- `exam_high_concurrency.jmx`（优化后）：测试高并发场景，30线程同步执行，登录P95=97ms（BCrypt cost=10优化后显著改善）
- `concurrency_consistency.jmx`：代码提交失败是因为业务逻辑（防重复交卷机制），系统行为正确，非脚本问题
- **数据矛盾说明**：`structexam-student-api.jmx`总体P95=14ms极低是因为包含97%的快速轮询请求（`/api/code/distributed/result`），掩盖了登录接口真实性能，统计失真

### 5.1.1 P95/P99 指标分析

#### 结论

**大部分历史 P95/P99 指标不正常** —— 要么**数值过高**（远超合理性能预期），要么**统计失真**（因混合场景导致百分位数失去业务意义），要么**长尾畸大**（P99 是 P95 的数十倍，暴露严重异常）。仅读接口（如考试列表、详情）的 P95（<20ms）属于正常范围。优化后部分指标已显著改善，但仍需持续关注。

#### 逐项判断

| 测试脚本 | 接口 | P95 | P99 | 是否正常？ | 原因 |
|----------|------|-----|-----|------------|------|
| `structexam-student-api.jmx`（历史） | 全链路 | 14ms | 47ms | **不正常** | 97%轮询请求拉低P95，掩盖登录（20~70秒）真实性能，统计失真 |
| `api_stability_test.jmx`（历史） | 登录 | 50,854ms | 62,670ms | **严重不正常** | 数值极端（>50秒），即使考虑BCrypt，也不该如此 |
| `concurrency_consistency.jmx`（历史） | 登录 | 10,705ms | 11,075ms | **不正常** | 10秒+仍然过高 |
| `availability_test.jmx`（历史） | 登录 | 16,473ms | 未给出 | **不正常** | 16秒+过高 |
| `reliability_fault_tolerance.jmx`（历史） | 登录 | 43,200ms | 56,206ms | **严重不正常** | 43秒，完全不可接受 |
| `login-only.jmx`（优化后） | 登录 | 5,085ms | 6,658ms | **基本正常** | 符合BCrypt cost=10在2核CPU下的预期（P95≈5秒） |
| `read-only.jmx`（优化后） | 登录 | 235ms | 351ms | **正常** | P95<300ms，符合预期 |
| `read-only.jmx`（优化后） | 读接口 | 7~9ms | 11~18ms | **正常** | P95<20ms，优秀 |

#### 具体异常表现

**1. 数值异常 —— 登录接口 P95/P99 普遍超过 10 秒，甚至 50 秒+**
- **正常期望**（BCrypt cost=10，2核CPU）：单次登录2~3秒，中低并发下 P95 < 5秒。
- **历史数据**：10秒 ~ 63秒。
- **根因**：单机Docker资源严重争用 + 请求排队，非代码缺陷，但说明测试环境无法支撑目标并发。

**2. 统计失真 —— 混合接口场景**
- `structexam-student-api.jmx`中97%轮询（响应<15ms）+ 3%登录（20~70秒），P95落在轮询区间（14ms），完全掩盖登录性能。
- **正确做法**：分离场景，分别计算各接口的P95/P99。

**3. 长尾畸大 —— P99 远大于 P95**
- `teacher-api.jmx`历史数据：P95=235ms，P99=14,874ms（相差63倍）
- `admin-api.jmx`历史数据：P95=207ms，P99=16,132ms（相差78倍）
- 说明存在极少数请求（可能是登录）响应时间暴涨，但被平均和P95掩盖。

**4. 优化后显著改善**
- **教师端登录**：P95从235ms降至175ms，P99从14,874ms降至262ms（改善98%）
- **管理员端登录**：P95从207ms降至176ms，P99从16,132ms降至214ms（改善99%）
- **高并发登录**：P95从20,808ms降至97ms（改善99.5%）
- **性能基线测试**：P95从50,854ms降至3,969.6ms（改善92%）
- **读接口**：P95<15ms，保持优秀水平
- **P99/P95比值**：从历史的63-78倍降至1.2-1.5倍，趋于正常

**5. 最新测试数据（2026-05-27）**
- **login-performance-baseline.jmx**：P95=3,969.6ms，P99=4,779.4ms，错误率24%
- **read-only.jmx**：登录P95=6,322.9ms，P99=7,008.5ms，错误率10%
- **exam_high_concurrency.jmx**：登录P95=97ms，P99=99ms，错误率0%
- **读接口性能**：P95<20ms，完全符合性能基线要求

#### 改进建议

1. **分离测试场景**：登录、读链路、写链路、轮询分别压测，独立计算P95/P99。即使做混合场景，报告中也应分接口列出分位数，不得合并计算。

2. **定义性能基线（SLA）**：登录P95<3秒，读接口P95<200ms，提交接口P95<1秒。未达标则结论为"**不通过**"，而不是"通过但需调查"。

3. **补充缺失的分位数**：确保所有测试脚本都记录并报告P95/P99数据，避免数据缺失。

4. **环境与资源配置**：若要测试系统在2核下的真实性能，必须确保`user-service`严格限制2核，且其他容器不争抢（或总CPU分配≤物理核数）。否则数据无法用于容量规划。

5. **监控长尾原因**：对P99异常高的场景，分析是哪些请求贡献了长尾（大概率是登录），针对性优化。

6. **修复接口问题**：`GET /api/question/{exam}` 接口100%失败，需排查后端实现或数据问题。

7. **降低登录错误率**：当前登录接口错误率较高（10-24%），需排查登录接口稳定性问题。

**总结**：原报告中的P95/P99大多不能作为系统性能合格的依据，优化后数据表明系统性能已显著改善（改善92-99%），但仍需按上述方向持续改进。读接口性能优秀，登录接口性能仍需优化。
