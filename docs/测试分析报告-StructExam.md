## 1 引言

### 1.1 编写目的

本报告对 **StructExam 全平台**（学生端、教师端、管理员端）在 **Docker 部署形态** 下的测试执行情况进行汇总，对照测试计划陈述**实际结果与发现**，给出功能与质量方面的**结论与评价**，并对缺陷、限制与后续工作提出建议。

**预期读者**：项目经理、测试负责人、前后端开发、运维、教学管理方（用户代表）。

### 1.2 背景

**a.** 被测软件系统名称：**StructExam 数据结构机考平台**（学生端、教师端、管理员端 Web + 经网关的 REST API）。

**b.** 任务提出者、开发者、用户及计算中心：以项目仓库及组织内立项/合同为准（本仓库未附任务书扫描件）。

**本次测试环境**：在 **Windows 10 + Docker Desktop 4.x** 上执行 **`docker compose up -d`**（项目根目录），包含以下服务：
- **基础设施**：`mysql:8.0`（端口映射 `3307:3306`）、`redis:7.0`、`nacos:2.2.3`
- **微服务**：`gateway`（端口 `8080`）、`user-service`、`exam-service`、`code-service`
- **前端**：`frontend`（Nginx 静态 + `/api` 代理，端口映射 `80:80`）
- **分布式判题**：`sandbox-node-1/2/3`（端口 `18091-18093`）
- **测试工具**：`playwright-tests`（容器化执行）、`jmeter`（容器化执行，`structexam-jmeter:latest`）

**Playwright** 使用 **`E2E_BASE_URL=http://frontend`**（Docker 网络内访问前端容器）及测试账号环境变量；**JMeter** 在 **容器内** 通过 `gateway:8080` 访问（Docker Compose 网络，直连网关）。

**容器资源限制**：
| 服务 | CPU限制 | 内存限制 |
|------|--------|----------|
| gateway | 2核 | 2GB |
| user-service | 2核 | 1GB |
| exam-service | 2核 | 1GB |

| frontend | 1核 | 512MB |
| sandbox-node-1/2/3 | 2核 | 2GB |
| playwright-tests | 4核 | 4GB |
| jmeter | 4核 | 4GB |

**测试环境与生产/机房环境的差异及影响**：

| 差异项 | 本次测试环境 | 对结果的影响 |
|--------|----------------|----------------|
| 单机 Docker | 全栈同机运行、无多副本与负载均衡 | 未验证 K8s 下调度与网络策略；性能指标受单机资源限制 |
| MySQL 宿主端口 | 因本机 **3306 已被占用**，映射为 **`3307:3306`** | 仅影响宿主机直连 MySQL 调试；容器内仍用 `mysql:3306` |
| 浏览器 | Playwright Chromium（容器内） | 兼容性结论不覆盖 Safari/Firefox 全矩阵 |
| JMeter 运行方式 | 容器化 JMeter（`structexam-jmeter:latest`，基于 `eclipse-temurin:17-jdk-alpine + JMeter 5.6.3`） | 避免 Docker Hub 拉取失败问题，测试结果更稳定 |
| 种子数据 | 使用 `sql/init.sql`（包含测试用户：admin01、teacher01、student01、jmeter_docker_01） | 与生产数据形态不同；生产环境需单独评估 |
| 沙箱节点 | 3 个 sandbox-node 节点本地运行 | 分布式判题能力已验证；生产环境需更多节点 |
| 网络环境 | 本地 Docker 网络，无外部网络延迟 | 未验证跨网络环境下的性能表现 |

### 2.2 实施过程中对环境的修改（相对仓库原状）

为打通 **Docker 内网关 → 各微服务** 及 **Docker 前端 → 网关 API**，本次对代码/配置做了如下变更（均已落库）：

| 项 | 说明 |
|----|------|
| `backend/gateway/.../application-docker.yml` | 新增：`docker` Profile 下路由 `uri` 使用 `user-service` / `exam-service` / `code-service` 主机名，Redis 使用 `REDIS_HOST`（默认 `redis`） |
| `docker-compose.yml` | `gateway` 增加 `SPRING_PROFILES_ACTIVE: docker`；`depends_on` 增加各业务服务；**MySQL 端口映射改为 `3307:3306`**；sandbox-node 镜像改为 Ubuntu 基础镜像以加速构建 |
| `frontend/nginx.conf` | **`proxy_pass` 去掉末尾 `/`**，保留完整 `/api/**` 路径转发至网关（修复 Docker 下登录接口 404/失败） |
| `Dockerfile.sandbox-node` | 将基础镜像从 Alpine 改为 Ubuntu（`eclipse-temurin:17-jdk-jammy`），解决 gcc/g++ 安装耗时过长问题 |

## 4 对软件功能的结论

### 4.1 功能 1（标识符：F-STU-AUTH，对应 TP-STU-01）

#### 4.1.1 能力

在 **Docker 全栈 + 修复后的 Nginx 反代** 下，学生可使用合法账号完成 **登录并进入首页**；网关 **登录接口** 在 JMeter 场景下 **零失败** 响应。上述能力经 **Playwright 1 项 + JMeter 链式取样** 证实。

#### 4.1.2 限制

- 未覆盖 **Token 刷新、登出、改密** 等全部分支。
- `init.sql` 默认学生账号与 README 明文密码 **可能不一致**，需在文档或脚本层面统一。

### 4.2 功能 2（标识符：F-STU-EXAM-READ，对应 TP-STU-02 子集）

#### 4.2.1 能力

在种子试卷 `exam_id=1`、题目 `question_id=1` 存在的前提下，**考试列表、考试详情、读取代码草稿** 接口在 JMeter 轻载下行为正常。

#### 4.2.2 限制

- 未验证 **进入考试、交卷、编程题保存** 等写路径。
- 考试列表接口的业务过滤逻辑未做专项断言（本次以 HTTP 200 与脚本通过为主）。

### 4.3 功能 3（标识符：F-STU-UI）

#### 4.3.1 能力

学生端 **壳层路由、登录/注册页** 在 Chromium 下表现正常。

#### 4.3.2 限制

未执行多浏览器矩阵；未执行 **考试页 Monaco** 重载与沙箱相关用例。

### 4.4 功能 4（标识符：F-TCH-MGMT，对应 TP-TCH-01～04）

#### 4.4.1 能力

教师端核心功能（认证、试卷管理、题目管理、考试监控）在 Docker 环境下正常工作；实时监控面板每 5 秒自动刷新，数据展示准确。
